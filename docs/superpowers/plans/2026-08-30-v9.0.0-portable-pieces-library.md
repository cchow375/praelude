## Release objective

Ship one normal CodaKiller build that Christian can use and send to another pianist. A fresh
installation starts as a blank, app-owned practice library. An upgrade preserves Christian's
database and configured or inferred score-folder location. There is no friend-specific fork and
no second product identity.

v9 also removes the bundled Knowledge/Resources experience and its copyrighted or
book-derived payload from the product and shareable artifact. That cleanup is deliberately
non-destructive: it does not delete Christian's external source folder and does not rewrite or
purge historical database conversation turns.

## Product contract

### 1. Pieces is the primary repertoire workspace

- The top-level destination is **Pieces Library**.
- Its local navigation is **Library | History | Calendar**.
- History remains available, but it is subordinate to Pieces rather than the product's primary
  repertoire entry point.
- Library rows expose a right-click menu and an equivalent ellipsis menu so the actions remain
  discoverable without knowing the context-menu gesture.

### 2. The user owns the organization

- Pieces may remain unfiled.
- Users may create nested logical folders and move pieces or child folders between them.
- Folder structure is application metadata, not a requirement to rearrange source files on disk.
- Folder moves reject cycles.
- Removing a folder promotes its child folders and pieces instead of cascading deletion.

This explicitly reverses the historical v8.1 decision that folders were out of scope. That old
decision remains factual in the immutable v8.1 record; it is not the current product contract.

### 3. Piece lifecycle is explicit

- A piece is **Active**, **Completed** or **Archived**.
- Right-click/ellipsis actions support changing that state and removing the piece from the
  visible library.
- Remove is recoverable: the managed piece folder is moved into the library's `.trash` area and the
  database row/history is retained.
- Removing a piece must never recursively delete an arbitrary path chosen by the user.

### 4. Direct PDF import is the normal path

- **Add Piece** accepts a title, optional composer, optional folder and a PDF already on disk.
- The app validates a regular, non-symlink `.pdf` with PDF content before copying it into the
  managed Pieces root.
- The original file remains untouched.
- A fixed external IMSLP discovery link is available, but it is not required to create a piece
  and the Add Piece form does not store an IMSLP URL.
- CodaKiller does not download the score from IMSLP. The user obtains a lawful copy, then imports
  it.

This explicitly reverses the historical IMSLP-first setup. Repertoire created through the older
flow remains usable after upgrade, but new-piece creation is local-PDF-first.

### 5. Fresh install and upgrade differ intentionally

Fresh profile:

- starts with no user repertoire/history and no bundled repertoire; the hidden system Warm-ups
  row and generic protocol template are internal scaffolding, not user pieces or practice data;
- creates an app-owned **Pieces** directory;
- shows a taught empty state and Add Piece flow;
- contains no Christian-specific score paths, PDFs or practice data.

Upgrade:

- migrates schema 20 to schema 21 in place;
- preserves the user's database and existing repertoire/history;
- uses the saved Pieces-root setting when present;
- otherwise conservatively infers the existing common score parent before falling back to the
  app-owned root;
- does not silently relocate existing scores.

### 6. Share-clean is a product invariant

The generic distribution must not contain:

- a user database, SQLite sidecars or database backup;
- repertoire PDFs, MusicXML or MXL files;
- Christian-specific local paths or personal practice data;
- the former bundled quote corpus, book/method payload or Knowledge/Books UI;
- private keys, secrets or provider credentials.

The checked-in share scan enforces the artifact-level boundary. Source cleanup removes the
bundled payload and product surfaces, but does **not** authorize deletion of the external
knowledge-source folder or historical database turns already owned by Christian.

### 7. Distribution boundary is plain

- Target: **Apple silicon Mac, macOS 13 or later**.
- Signing: local/ad-hoc unless a later release record proves otherwise.
- Notarization: **not provided** in this plan.
- A recipient may need Control-click → Open or Privacy & Security → Open Anyway.
- Those Gatekeeper steps must appear in the package's `START_HERE.txt` and the user guide.

## Data design

v9 targets **schema 21**.

- `piece_folder` stores the logical folder tree.
- Each piece may hold a nullable `folder_id`.
- `completed_at` distinguishes Completed from Active without erasing practice history.
- `metadata_source` distinguishes user-entered title/composer metadata from scanner-derived
  metadata so a later rescan does not overwrite the user's naming.
- Existing archived state remains authoritative for Archived.

Migration requirements:

1. Existing rows, IDs, paths, sessions, rep blocks, reps, events and contracts survive exactly.
2. Existing pieces default to unfiled unless the user later organizes them.
3. No migration step moves a score file.
4. Integrity and foreign-key checks must pass after rehearsal and installed launch.
5. A failed migration must leave the outgoing v8.2.1 app and pre-install database backup usable.

## File-safety rules

- Import copies into a controlled path beneath the configured Pieces root.
- Source PDFs are never modified or deleted.
- File names are sanitized and collisions receive a bounded unique name.
- Symlink inputs and non-PDF content are rejected.
- Remove operates only on the exact, database-selected repertoire file and only when it is a
  direct managed child of the configured root.
- A database failure after copying quarantines the managed copy instead of pretending success.
- Folder operations affect metadata only.

## Open-session and install safety

Release/install work must not begin while CodaKiller has an open practice session, active rep
contract or another running app instance.

Before replacing `/Applications/CodaKiller.app`:

1. Inspect the live database read-only and record schema, row counts, integrity, foreign keys,
   open sessions and active contracts.
2. If a session or contract is open, stop. Christian must finish or deliberately close it in the
   outgoing installed app; release scripts must not manufacture session closure.
3. Quit the app and verify there is no running CodaKiller process.
4. Create and hash a pre-install database backup and an outgoing-app rollback archive.
5. Rehearse schema 20→21 on a disposable copy, never the live database.
6. Install only after the rehearsal, package and signature checks pass.
7. Launch the installed app once, quit cleanly, then repeat the exact read-only audit.
