## Task 1: Close the B56 residual (carried from P0)

**Why:** P0 closed the exporter-side TOCTOU but left a narrower opener-side window, documented in `NOTES.md` and in the vault flaw register. `rep/mod.rs:277` calls `ensure_session()`, which **releases** `lifecycle` on return; `self.active` is locked on the next line, `:278`. Between them an exporter holding `lifecycle` can see `active == None`, export and end session S — while the opener already holds S in `session_hint` and writes its block against it at `:288`. Same mis-attribution class as B56, smaller window. P0 deliberately deferred this because the complete fix touches the hot path that produced three deadlock classes over three fix rounds; it gets a proper design pass here rather than an improvisation.

**Files:**

- Modify: `src-tauri/src/sessions/mod.rs`, `src-tauri/src/rep/mod.rs`
- Test: both files' `#[cfg(test)] mod tests`

**Interfaces:**

- Consumes: `SessionService::end_and_export_guarded<E>` (added in P0), the lattice `lifecycle < current < pause_hook < active < store.conn`, and the invariant _no path may hold `rep.active` across a `SessionService` call_.
- Produces: `SessionService::with_session_locked<R>(&self, f: impl FnOnce(Option<i64>) -> R) -> R` — resolves the session and runs `f` **with `lifecycle` still held**, so the caller can mutate `rep.active` inside the same critical section. Taking `lifecycle` then `active` is lattice order and therefore deadlock-free.

- [ ] **Step 3: Implement `with_session_locked`**

In `sessions/mod.rs`, mirroring `end_and_export_guarded`'s shape. It must resolve the session using the **same** internal path `ensure_session` uses, but without releasing `lifecycle` before the closure runs.

```rust
    /// Resolve the current session and run `f` with `lifecycle` STILL HELD.
    ///
    /// Closes the opener-side half of B56. `ensure_session()` releases
    /// `lifecycle` when it returns, so a caller that then locks `rep.active`
    /// has a window in which an exporter can end the very session it just
    /// resolved. Holding `lifecycle` across both is lattice order
    /// (`lifecycle` → `active`) and therefore deadlock-free.
    ///
    /// `f` MUST NOT call back into `SessionService` — this lock is not
    /// reentrant. It may take locks strictly below `lifecycle` in the lattice,
    /// which is exactly what `rep.active` and `store.conn` are.
    pub fn with_session_locked<R>(&self, f: impl FnOnce(Option<i64>) -> R) -> R {
        let _lifecycle = self
            .lifecycle
            .lock()
            .unwrap_or_else(|poison| poison.into_inner());
        let sid = self.resolve_session();
        f(sid)
    }
```

Verify by reading that `resolve_session` does not itself take `lifecycle` (it takes `current`) — if it does, extract a `_locked` variant rather than nesting the lock.

## Task 3: A1 — tempo demotion ("the punishment")

**Why (spec §5.1):** Christian's words: _"there needs to be more punishment."_ Today the ladder only climbs (`ladder::step`, `:103-118`); the sole decrease is the manual `tempo_backoff` recovery action. After **3 consecutive sloppy reps** the ladder must step DOWN one rung; while demoted the threshold drops to **2**. A clean rep resets the counter. The floor is the set's `start_bpm`. **"Again"/`failed` does not count** — Christian's explicit answer.

**Design consequence of the recon:** because `project_tempo` replays the ledger, demotion is computed, not stored. Track a `sloppy_streak` beside `clean_streak` in the same loop.

**Ambiguity resolved here (state the assumption, do not stall):** "while demoted, the threshold is 2" is read as _once a demotion has occurred in this set, the repeat threshold applies for the remainder of the set_. Simple, predictable, and matches "more punishment". Re-climbing uses the normal ladder rules.

**Files:**

- Modify: `src-tauri/src/store/model.rs` (`IncrementRule` gains defaulted demotion fields; `RepSnapshot` gains the counter)
- Modify: `src-tauri/src/store/practice_v2.rs` (`project_tempo`, `:397-441`)
- Modify: `src-tauri/src/settings.rs` (three new settings)
- Modify: `src-tauri/src/rep/mod.rs` (pass the resolved config into the store call — **not** read inside the lock)
- Modify: `src/features/rep/RepHud.tsx` (the visible moment)
- Test: `practice_v2.rs`, `settings.rs`, `RepHud.test.tsx`

**Interfaces:**

- Produces: `IncrementRule { clean_needed, bpm_step, demote_enabled: Option<bool>, demote_first: Option<u32>, demote_repeat: Option<u32> }` — all three new fields `#[serde(default)]` and `Option`, so `None` means "use the global setting" and old stored JSON (and the **nullable** `increment_rule` column) loads unchanged.
- Produces: settings `rep.demote_enabled` (bool, default **true**), `rep.demote_first` (u32, default 3, bounded 2–10), `rep.demote_repeat` (u32, default 2, bounded 1–10).
- Produces: `RepSnapshot.current_sloppy_streak: u32` and `RepSnapshot.demoted_this_set: bool`.

> **Lock trap — do not read settings inside the projection.** `project_tempo` runs inside the store, and `Store::get_setting` takes the same `conn` mutex; reading settings there risks re-entering a non-reentrant lock. Resolve the demotion config in `rep/mod.rs` **before** the store call and pass it in as a parameter.
